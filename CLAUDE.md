# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Street Scene is a browser street racer (TypeScript, three.js, Vite, Vitest; no framework, no linter or formatter): night races through a seeded procedural city with a deterministic arcade sim, AI rivals, a garage, replays and ghosts. README.md holds the player-facing docs (controls, credits, the decisions log); read it only when a task touches those.

## Commands

| Task | Command |
|---|---|
| Dev server, pinned to port 5175 (`strictPort`) | `npm run dev` |
| Typecheck, about 1 s (`noUnusedLocals`/`Parameters` are errors) | `npm run typecheck` |
| Tests, about 35 s (Vitest, node env, 120 s per test) | `npm test` |
| One file, one test | `npx vitest run tests/sim.test.ts -t "nitrous"` |
| Production build (typecheck + vite build) | `npm run build` |
| Validate the parts catalog against `public/` | `npm run validate` |
| Inspect a GLB (nodes, materials, triangles) | `npm run inspect -- public/cars/s64.glb` |
| Rebuild car assets from FBX (slow, rewrites generated files) | `npm run assets` |
| Import music / rebuild the music catalog (needs ffmpeg) | `npm run music` |

Project skills wrap these: `/check [file] [-t name]` runs typecheck + tests and prints only failures; `/map [dir]` prints a one-line-per-module map of the source; `/dev` runs the game in a browser; `/district`, `/tune` and `/assets` are step-by-step guides for those jobs. `.claude/rules/` adds path-scoped guidance when you edit sim, render, test or data files.

## Architecture

Data flows one way: seed → city → world → sim → session → render.

- `src/city/` (pure): `roadGraph` → `districts/` (special areas plan and build) → `blocks` (sidewalks, buildings, walls, street furniture) → `terrain` → `route` (circuit/sprint/drift, barriers, corner rails). `world.ts` assembles the `World` the sim queries (`heightAt`, `surfaceAt`, `collideCircle`, route progress); it is built once per race and never mutated. `config.ts` holds every generation constant (`CITY`, `ROUTE`).
- `src/sim/` (pure): `race.ts` owns `RaceState` (`createRace`, `stepRace` once per 60 Hz tick); `car.ts` physics (two substeps), `collision.ts`, `ai.ts` (AI lives inside the sim), `rails.ts` (heavy dentable rail pieces), `props.ts` (destructibles), `build.ts` (performance tiers → tuning via `applyBuild`), `tuning.ts` (types, merges and validates `drivingParams.json`), `stats.ts` (0-100 and top speed measured by driving the sim). One `InputFrame` per tick, quantized and packed to 4 bytes (`input.ts`); the packed log is the replay.
- `src/game/session.ts` (`RaceSession`) is the bridge: `tick()` steps the sim with live input or a recorded log; `render(alpha, dt)` interpolates the previous and current snapshots and drives the three.js scene, camera, HUD, engine audio and SFX. `main.ts` is boot plus the state machine (menu, race, garage, drone, freefly) around `FixedStepLoop` (`loop.ts`).
- `src/render/`: three.js only, reads state. `scene.ts` (`GameRenderer`, `createNightScene`) composes `cityMeshes`, `districts/`, `props`, `roadblocks`, `routeArrows`, `crowds`, `lightFx`, `post`. `carView.ts` + `carAssets.ts` build cars and parts from the manifest and catalog; `autoQuality.ts` adapts quality to frame time.
- `src/garage/` garage scene, UI and `storage.ts` (slots, share codes); `src/replay/` replays, ghosts, bests; `src/audio/` music player and synthesized engine/SFX; `src/ui/` HUD, screens, panels, Lucide icons; `src/input/` keyboard, gamepad and touch → `InputFrame`.
- Districts are paired modules: `src/city/districts/<kind>.ts` (a `DistrictModule` with `plan`/`build`, registered in a fixed order in `index.ts`) and `src/render/districts/<kind>.ts` (a `DistrictRenderer` appending into a shared kit of merged builders). Every sim wall carries a `look`, and every look has a renderer, so collision always matches what is drawn.
- Data: `src/sim/drivingParams.json` (every physics number; `base` + `cars.<id>` overrides merged key by key, arrays replace whole, `_` keys are comments, unknown keys throw at startup); `src/assets/carManifest.json` (car geometry, `selectable`); `src/assets/partsCatalog.json` (entries with `"generated": true` are rewritten by `npm run assets`); `src/assets/musicCatalog.json` (fully generated by `npm run music`). `src/shared/parts.ts` is the slot and material vocabulary shared by renderer, garage and asset scripts.

## Invariants (the tests enforce most of these)

1. `src/sim/` and `src/city/` are pure and deterministic: no DOM, `window`, three.js, `Math.random`, `Date`, `performance.now` or frame time. Randomness only through the seeded `Rng` (`sim/prng.ts`; `deriveSeed` for sub-streams), trig through `sim/math.ts`. Same seed + build + input frames ⇒ identical state, bit for bit.
2. Rendering only reads state. Nothing under `render/`, `game/`, `garage/`, `ui/` or `audio/` writes into `RaceState` or `World`.
3. `CarBuild = { visual, performance }`: only the renderer reads `visual`; the sim reads `performance` through `applyBuild`. Visual choices never change tuning.
4. All physics numbers live in `drivingParams.json`; no tuning magic numbers in sim code.
5. Every sim wall is drawn by something, and nothing drawn stops a car without a wall.
6. Because of 1, any behaviour change in `sim/` or `city/` changes every existing replay, ghost and best time for that seed. Say so when it happens.

## Conventions

- Strict TS, ES2022 modules, JSON imports, `import type` for type-only imports. Single quotes, semicolons, trailing commas, long lines are fine; match the surrounding file. Unused imports or locals fail the typecheck.
- Every module starts with a `/** ... */` comment saying what it does and why; interface fields get one-line JSDoc with units (m, s, ticks, rad, kg). Comments explain reasoning and trade-offs, not what the code already says. Keep that density.
- Constants are `as const` tables (`CITY`, `ROUTE`, `RAIL`, `CAMERA`, `QUALITY`) next to the code that uses them.
- Tests use `tests/helpers.ts` (`flatWorld`, `raceConfig`, `runAutopilot`, `replayLog`, `carSnapshot`, `input`) and prove determinism by running twice and comparing `JSON.stringify` snapshots, often over many seeds.
- Commits: short imperative subject, then a body grouped by area (Garage / City / Physics ...) with `-` bullets. Commit only when asked.

## Working efficiently

- Orient with `/map` or `grep -rn "export .* <name>" src` instead of reading files to find things. Largest files: `ui/ui.css` 1.3k lines, `render/finishLine.ts` 1.2k, `audio/sfx.ts` 1k, `garage/garageUi.ts` 960, `city/route.ts` 950, `city/blocks.ts` 790; read those in ranges.
- Never read `public/` media, `assets/source/` FBX or `package-lock.json` (denied in settings). For a GLB use `npm run inspect -- <file>`; `assets/inspect.md` is the last asset report; `npm ls <pkg>` gives versions.
- Verify with `/check`: typecheck after every edit, the full suite after touching `src/sim/` or `src/city/` (replay determinism, many-seed AI and rail sweeps). Headless beats the browser: `npx tsx` imports any `src/sim` or `src/city` module directly (`/tune` measures a car that way, `scripts/debugCitySvg.ts <seed> out.svg` draws a city).
- `node_modules` must exist (`npm ci`). `npm run assets` and `npm run music` rewrite generated files and need external tools; run them only when the task is about assets or music.
- The Blender MCP server in `.mcp.json` needs `uv` installed (`brew install uv`); it is only for modelling work and its connection failure is otherwise harmless.
