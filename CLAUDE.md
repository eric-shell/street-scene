# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Street Scene is a browser street racer (TypeScript, three.js, Vite, Vitest, SCSS; no framework outside the admin dashboard, no linter or formatter): night races through a seeded procedural city with a deterministic arcade sim, AI rivals, a garage, replays and ghosts. README.md holds the player-facing docs (controls, credits, the decisions log); read it only when a task touches those.

## Commands

| Task | Command |
|---|---|
| Dev server, pinned to port 5175 (`strictPort`) | `npm run dev` |
| Typecheck, about 1 s (`noUnusedLocals`/`Parameters` are errors) | `npm run typecheck` |
| Tests, about 35 s (Vitest, node env, 120 s per test) | `npm test` |
| One file, one test | `npx vitest run tests/sim.test.ts -t "nitrous"` |
| Browser tests, about 50 s per spec and 5+ min for all (Playwright, Chromium, software WebGL; starts the dev server if needed) | `npm run e2e -- e2e/raceMap.spec.ts` (`-g "music"` narrows further) |
| Production build (typecheck + vite build) | `npm run build` |
| Validate the parts catalog against `public/` | `npm run validate` |
| Screenshot the analytics dashboard against stubbed data at five widths (overflow, gutter, pager; writes nothing) | `npm run check:dashboard -- http://localhost:5175 <outDir>` |
| Inspect a GLB (nodes, materials, triangles) | `npm run inspect -- public/cars/protoHatch.glb` |
| Audit a shipped car against its reference spec (proportions, pillars, mirrors, handles, lamps) | `npm run audit -- protoHatch` |
| Rebuild car assets from the authored .blend cars and FBX imports (needs Blender, rewrites generated files) | `npm run assets` |
| Import music / rebuild the music catalog (needs ffmpeg) | `npm run music` |
| Rebuild the traffic vehicles from the Comrade1280 packs (needs Blender, rewrites generated files) | `npm run traffic` |

Project skills wrap these: `/check [file] [-t name]` runs typecheck + tests and prints only failures; `/map [dir]` prints a one-line-per-module map of the source (`/map .scss` lists the style partials); `/dev` runs the game in a browser; `/district`, `/tune`, `/assets`, `/car` (a car or kit from reference vehicles) and `/blender` are step-by-step guides for those jobs; `/refactor` moves files with their imports, finds dead exports, and proves a refactor changed nothing (golden sim/city hashes, the CSS cascade, the three.js scene, the UI's computed styles). `.claude/rules/` adds path-scoped guidance when you edit sim, render, style, test or data files. Hooks check edits as they land: a `.json` data file must parse and validate, a `.scss` edit must compile without Sass warnings, and Blender MCP code is screened for known crashers.

## Checks: run only what the change justifies

Typecheck, Vitest, e2e, `/dev` and `/refactor`'s proofs cost minutes and many tokens, and most prompts need none of them. The default is to run nothing. Each check must be earned by what this prompt changed, never run as a habit, a closing ritual or "to be safe".

| What changed | What to run |
|---|---|
| Docs, comments, copy, README, `.claude/`, questions and exploration | Nothing |
| A `.json` data file or a `.scss` partial | Nothing: the hooks already validate and compile it |
| Car, part or Blender assets | `npm run audit` / `inspect` when the task is about the asset; no tests |
| TS outside `src/sim/` and `src/city/` (render, ui, game, garage, audio, input, scripts) | Typecheck once after the edits (`/check tsc`, 1 s), not after each edit. Add a Vitest file only if `grep -ln <module> tests/` finds one and the change could alter what it asserts |
| `api/` (account, analytics, admin) | `tests/analytics.test.ts` (PGlite, under 1 s) for analytics or admin SQL; typecheck for the rest |
| `src/admin/` (the dashboard) | Typecheck; `npm run check:dashboard` when layout or styles change |
| `src/sim/` or `src/city/` | The one covering test file (`/check tests/x.test.ts -t name`) |
| Sim or city behaviour actually changed | The full suite (`/check`, 35 s), once, at the end of the task. Not for renames, comments, refactors proven by `/refactor`'s golden hashes, or tuning already measured with `/tune` |
| A flow only a real page can show | One e2e spec (`npm run e2e -- e2e/<spec>`, 50 s, 180000 ms timeout, never piped through `tail`): `splash` (boot, deep links, opening track), `musicAutoplay`, `audioMix` (levels), `engine` (engine worklet), `gamepad` (pad menus, rumble, auto pause), `freeRoam` (menu-to-roam handoff), `raceMap` (the race's city map). The whole e2e suite only when the user asks |

- Never re-run a check that passed on code you haven't touched since, and never run a broader check than the table calls for because a narrower one passed.
- `/dev` and screenshots only when the user asks or a visual change cannot be judged from the code.
- Add a new test only when asked, or when a fix has no other coverage and is likely to regress.
- When you skip a check the user might expect, say so in one line (what and why) so they can ask for it.

## Architecture

Data flows one way: seed → city → world → sim → session → render.

- `src/city/` (pure): `roadGraph` → `districts/` (special areas plan and build) → `blocks` (sidewalks, buildings, walls, street furniture) → `terrain` → `routeSearch` (picks the node paths: circuit and sprint with the city, drag and waypoint from the finished city) → `route` (`buildRoute`, `routeSample`) with `routeBarriers` (side street closures) and `routeRails` (corner rails); `graphSearch` holds the heap and Dijkstra. `world.ts` assembles the `World` the sim queries (`heightAt`, `surfaceAt`, `collideCircle`, route progress); it is built once per race and never mutated. `config.ts` holds every generation constant (`CITY`, `ROUTE`). `events.ts` names each seed's event flavour and supplies the route preference; planners after the route pick read the routes from `PlanContext.event`. `railTimetable`/`railCurve` live here so the level crossing's gates and the trains agree; `levelCrossings.ts` builds the timed gates.
- `src/sim/` (pure): `race.ts` owns `RaceState` (`createRace`, `stepRace` once per 60 Hz tick); `car.ts` physics (two substeps), `collision.ts`, `ai.ts` (AI lives inside the sim), `rails.ts` (heavy dentable rail pieces), `props.ts` (destructibles), `build.ts` (the four 1-5 setup sliders and launch rpm → tuning via `applyBuild`), `tuning.ts` (types, merges and validates `drivingParams.json`), `stats.ts` (0-100 and top speed measured by driving the sim), `reset.ts` (every reset and tow of a car). `gates.ts` (timed gates: pure schedules of the tick, collision, AI waiting), `traffic.ts` (ambient civilian cars; `RaceConfig.traffic`, off when missing), `driftZones.ts` (zone multiplier and nitrous refill). One `InputFrame` per tick, quantized and packed to 4 bytes (`input.ts`); the packed log is the replay.
- `src/game/session.ts` (`RaceSession`) is the bridge: `tick()` steps the sim with live input or a recorded log; `render(alpha, dt)` interpolates the previous and current snapshots and drives the three.js scene, camera, HUD, engine audio and SFX. `main.ts` is boot plus the state machine (menu, race, garage, drone, freefly; a race session is a race or free roam) around `FixedStepLoop` (`loop.ts`). `streetStage.ts` is the menu city: the event world and night scene with the player's car cruising the route (render only; it waits at timed gates on its own clock), shot by `streetCameras.ts` (`ShowreelCamera` behind the menu, `FollowOrbit` for the garage's Street view); the drone and free camera fly over it.
- `src/render/`: three.js only, reads state, grouped by what is drawn. The root holds the frame: `scene.ts` (`GameRenderer`, `createNightScene`) composes everything with `post`, `lighting` and `autoQuality.ts` (adapts quality to frame time); `geoBuilder` merges geometry. `street/` (`cityMeshes`, decals, furniture, destructible `props` and their debris, `lightFx` street light pools, `areaLights` park and plaza light), `buildings/` (`architecture` neighbourhood and style plan → `buildings` merged meshes with `facadeAtlas` / `facadeMaterial`, wall dressing), `race/` (`finishLine`, `routeArrows`, `meetPlan` places the street meets behind every cyan barrier that `crowds` and `roadblocks` draw, waypoint beacons), `car/` (`carView` + `carAssets` build cars and parts from the manifest and catalog; `sparks` from sim telemetry), `camera/`, `sky/` (backdrop, weather, lightning), `people/` (`person` is the one character everyone is: the garage crew now, crowds and the driver next; `docs/people.md`), `traffic/` (`traffic` draws the civilian cars from `public/traffic/` in one BatchedMesh; `trains`, air traffic), `textures/` (canvas textures through `canvasKit`: street, sign, decal and graffiti atlases each in their own module), `districts/`; `disposer.ts` (`track` every GPU resource), `materialFx.ts` (sub-pixel fade, the fog-fading road wash) and `color.ts` sit at the root. The elevated railway is `districts/subway` plus `railCurve`, `railTimetable` and `traffic/trains`.
- `src/garage/` garage scene (`showroom.ts` is the workshop room with the lifts and their cars, built from `showroomProps` merged primitives, `showroomTextures` canvases and the `neonSign`s; the Street view borrows the street stage), UI and `storage.ts` (slots, share codes); `src/replay/` replays, ghosts, bests; `src/audio/` music player, SFX (`sfx.ts` the player, `sfxRecipes` the impact DSP, `sfxVoices` the drive's loops and levels, `crowdAudio`, `sceneVoices` the train, helicopter and thunder) and the engine voices (`engineSynth.ts` is the pure pulse-train synth and its programs from an `EngineSpec` (`SYNTH_PARAMS` is the worklet's parameter contract, `dsp.ts` the biquad and K-weighting), `engineWorklet.ts` runs it on the audio thread, `engineAudio.ts` wraps it with the silencer convolution, intake, turbo and levels, and holds the mixer: engine, effects, ambience and interface buses under a master, each a Sound setting; `docs/engineSound.md` has the voice model and the plan per layout, `docs/audioMix.md` the balance every sound is set against, guarded by `e2e/audioMix.spec.ts`); `src/ui/` is grouped by screen, each TS module with its SCSS partial beside it: `kit/` (the DOM helpers `h`, `bem`, `btn`, `segmented`, `chip`, Lucide icons, the canvas palette, formats and US units, and the shared components' styles), `rail/` (the layout every menu screen shares: rail, steps, screen header, rows of places, `railInset` for `GameRenderer.setFraming`), `menu/` (the main menu and its city and course maps), `splash/`, `screens/` (pause, results, the settings panel, loading), `transitions/` (wipe, roller door), `hud/` (HUD, `minimap` shared by the HUD and the drone, the HUD card, nitrous callouts, hazard banner), `map/` (the city map layers, place names, and the full map modal: the class plus its camera, painters, tags, card and side panel), `panels/` (help, music player, tuning panels) and `settings.ts`; `styles/main.scss` holds the design notes, the naming and nesting conventions (BEM, `.claude/rules/styles.md`) and the cascade order, `styles/base/` the tokens and document layer, `styles/abstracts/` the palette, breakpoints and mixins; `src/input/` keyboard, gamepad and touch → `InputFrame`.
- Accounts (`docs/accounts.md`): `api/account.ts` is one of three Vercel functions (Hobby allows 12) (Google ID token sign-in for an `ALLOWED_EMAILS` list, an HMAC session cookie, one Neon `players` row holding the synced save as JSONB; `db/schema.sql`, `npm run db:init`), served in dev by `scripts/apiDev.ts`. `src/account/` syncs the garage, its prefs and the settings through `shared/store`'s `onSaved`; `main.ts` awaits `accountReady` before reading saved state. Builds without `VITE_GOOGLE_CLIENT_ID` have no accounts.
- Analytics (`docs/analytics.md`): `src/analytics/` is the game's beacon (visitor and visit ids, one page view per load, heartbeats that back off and stop 3 minutes after the last input, typed events from `src/shared/analytics.ts`, a per-drive frame-rate summary; off under GPC/DNT, `navigator.webdriver`, `npm run dev` without `?analytics`, and the Settings → Privacy switch). `api/analytics.ts` writes it (always 204, rate limited per IP by `api/_lib/rateLimit.ts`); `api/admin.ts` is every dashboard op behind Google sign-in plus `ADMIN_EMAILS`, and the daily prune for Vercel Cron (`vercel.json`). The dashboard is `/dashboard` → `dashboard.html` → `src/admin/`: the one place React and visx are allowed, its own Vite page so the game never loads them, styled with SCSS on the game's tokens and kit (no Tailwind). The schema's analytics tables share the accounts' Neon database.
- Free tiers only: Vercel Hobby, Neon free, no paid add-ons (Upstash is deliberately off). Anything that polls or beats must stop when nobody is at the screen, since Neon's free compute is a monthly allowance and running out takes accounts down too.
- Districts are paired modules: `src/city/districts/<kind>.ts` (a `DistrictModule` with `plan`/`build`, registered in a fixed order in `index.ts`) and `src/render/districts/<kind>.ts` (a `DistrictRenderer` appending into a shared kit of merged builders). Every sim wall carries a `look`, and every look has a renderer, so collision always matches what is drawn.
- Data: `src/sim/drivingParams.json` (every physics number; `base` + `cars.<id>` overrides merged key by key, arrays replace whole, `_` keys are comments, unknown keys throw at startup); `src/assets/carManifest.json` (car geometry, `selectable`, the `engine` spec); `src/assets/partsCatalog.json` (entries with `"generated": true` are rewritten by `npm run assets`); `src/assets/musicCatalog.json` (fully generated by `npm run music`); `src/assets/trafficModels.json` (fully generated by `npm run traffic`: each traffic kind's footprint, lamps and the CC BY credits; `traffic.kinds` in `drivingParams.json` must match its footprints). `src/shared/parts.ts` is the slot and material vocabulary shared by renderer, garage and asset scripts; `src/shared/carBuild.ts` is the whole car build the garage saves and shares (the visual half and validation; `sim/build.ts` keeps the performance half, the only part the sim reads); `src/shared/carSpec.ts` is the engine layout / drivetrain code vocabulary (garage badges, engine voice, validation). `scripts/blender/carSpecs.json` is each car's reference spec (two real donors with sourced dimensions, the house stylization, lamp signatures); `docs/carDesign.md` is the design language the audit and the Blender feature builders enforce.

## Invariants (the tests enforce most of these)

1. `src/sim/` and `src/city/` are pure and deterministic: no DOM, `window`, three.js, `Math.random`, `Date`, `performance.now` or frame time. Randomness only through the seeded `Rng` (`sim/prng.ts`; `deriveSeed` for sub-streams), trig through `sim/math.ts`. Same seed + build + input frames ⇒ identical state, bit for bit.
2. Rendering only reads state. Nothing under `render/`, `game/`, `garage/`, `ui/` or `audio/` writes into `RaceState` or `World`.
3. `CarBuild = { visual, performance }`: only the renderer reads `visual`; the sim reads `performance` through `applyBuild`. Visual choices never change tuning.
4. All physics numbers live in `drivingParams.json` (the sliders' tables in its `setup` section); no tuning magic numbers in sim code.
5. Every sim wall is drawn by something, and nothing drawn stops a car without a wall.
6. Because of 1, any behaviour change in `sim/` or `city/` changes every existing replay, ghost and best time for that seed. Say so when it happens.

## Frame-rate targets

Aim for 120 fps, hold 60 fps on every supported device, never drop below 30 fps. In frame time: 8.3 ms is the goal, 16.7 ms is what everything per frame has to fit at Medium on a mid device, 33 ms is the failure line. `FRAME_BUDGET` in `src/render/frameBudget.ts` (re-exported by `autoQuality.ts`) is the one place these numbers live; the auto quality controller, the FPS meter and these docs read them from there.

- The sim ticks at 60 Hz whatever the frame rate: at 120 fps every other frame is pure interpolation (`alpha`), at 30 fps two ticks run per frame, so a tick's cost counts double at the floor. Anything per frame in `render/`, `game/`, `ui/` or `audio/` scales with `dt` (exponential smoothing, never a per-frame lerp factor) so 30, 60 and 120 fps look the same.
- Auto graphics (`AutoQualityController`) buys quality only with headroom at the aim (120 fps capped at the display's refresh rate, which it learns from the fastest frames it has seen), steps down one level after a few seconds below 60, drops two levels on the first evaluation at 30, and holds anywhere in between. A probe that leaves the aim or slips below 60 is reverted and backed off.
- New visual work fits the ladder: give it a knob in `QUALITY_LEVELS` / `QUALITY` or a tier gate rather than a fixed cost, and keep allocations and per-object draw calls off the per-frame path. A feature that cannot hold 60 at Medium belongs in High or needs a cheaper form.
- Measure before and after with `?fps` (fps, frame time in ms, auto level and its aim; `/dev`); the controller's stats are on `window.__nr.autoQ`. When a change adds per-frame or per-tick work, say what it costs.

## Conventions

- Strict TS, ES2022 modules, JSON imports, `import type` for type-only imports. Styles are SCSS partials beside the TS that builds their DOM, BEM classes nested per block (`src/ui/styles/main.scss`, `.claude/rules/styles.md`). Single quotes, semicolons, trailing commas, long lines are fine; match the surrounding file. Unused imports or locals fail the typecheck.
- Every module starts with a `/** ... */` comment (a `/* ... */` in a style partial) saying what it does and why; interface fields get one-line JSDoc with units (m, s, ticks, rad, kg). Comments explain reasoning and trade-offs, not what the code already says. Keep that density.
- Physics is simcade (`docs/handling.md`, Simcade): real foundations (the tire model, load transfer, a drag-set top speed, donor gearboxes, brake bias, the differential) with named arcade aids on top. Start from the real behaviour and measure it (`/tune`); add an arcade term only where realism does not deliver the feel, as one labelled number in `drivingParams.json` that is neutral when off. Never fake the foundation.
- Reach for the shared helpers before writing another copy: `sim/math` (clamp, clamp01, lerp, wrapAngle, wrapIndex, smoothstep), `shared/anim` (`damp(rate, dt)` for frame-rate independent smoothing), `shared/store` (localStorage under `nightrun.`), `render/disposer` (`track` every GPU resource), `render/textures/canvasKit` (canvas textures, `fitFont`), `render/materialFx`, `ui/kit/dom` (`h`, `bem`, `btn`, `isTyping`, `prefersReducedMotion`).
- Constants are `as const` tables (`CITY`, `ROUTE`, `RAIL`, `CAMERA`, `QUALITY`) next to the code that uses them. A new module goes in the folder of what it does (`.claude/rules/render.md` lists the `render/` folders); a subfolder earns its place at about four related modules.
- Tests use `tests/helpers.ts` (`flatWorld`, `raceConfig`, `runAutopilot`, `replayLog`, `carSnapshot`, `input`) and prove determinism by running twice and comparing `JSON.stringify` snapshots, often over many seeds.
- Commits: short imperative subject, then a body grouped by area (Garage / City / Physics ...) with `-` bullets. Commit only when asked.

## Working efficiently

- Orient with `/map` or `grep -rn "export .* <name>" src` instead of reading files to find things. Largest files: `ui/map/fullMap.ts` 1.3k (one stateful class), `city/config.ts`, `garage/showroom.ts`, `sim/car.ts`, `render/traffic/airTraffic.ts` and `city/districts/subway.ts` 1.1k, `city/blocks.ts`, `game/session.ts` (`RaceSession`; its helpers in `game/session/`) and `city/districts/alleyShortcuts.ts` 1k (one 530-line planner); read those in ranges. Big modules split into a folder beside their entry module, which still exports everything (`sim/ai/`, `sim/traffic/`, `districts/carPark/`, `river/`, `highway/`, `garage/props/`, `garage/textures/`). Style partials are one block each, a few hundred lines at most (`/map .scss`).
- Never read `public/` media, `assets/source/` FBX or `package-lock.json` (denied in settings). For a GLB use `npm run inspect -- <file>`; `assets/inspect.md` is the last asset report; `npm ls <pkg>` gives versions.
- Checks follow the budget in **Checks** above; don't run them out of habit.
- Headless beats the browser: `npx tsx` imports any `src/sim` or `src/city` module directly (`/tune` measures a car that way, `scripts/debugCitySvg.ts <seed> out.svg` draws a city).
- `node_modules` must exist (`npm ci`). `npm run assets`, `npm run music` and `npm run traffic` rewrite generated files and need external tools; run them only when the task is about assets, music or traffic.
- The Blender MCP servers (`blender` drives the scene, `blender-lab` searches the Blender API docs and manual) live in `.claude/skills/blender/mcp.json` and load only in a session started with `claude --mcp-config .claude/skills/blender/mcp.json`, so ordinary sessions never pay for them; they need `uv` installed (`brew install uv`) and are only for modelling work. Read `/blender` before driving them; `.claude/skills/blender/mcp.sh` checks, installs and upgrades both with their Blender add-ons (runbook: `.claude/skills/blender/mcp.md`).
- Delegate to the `worker` agent, never `fork`: a fork always runs on the session's model. Choose the worker's model for the task with the Agent tool's `model`, and name it with a reason when you spawn it: `haiku` for mechanical work (moving files, renames, data edits, running a script and reporting), `sonnet` for ordinary implementation (a module change, a district pass, a fix whose cause is known), `opus` only when the task needs deep reasoning (sim or city behaviour and determinism, a design across many modules, a bug with no known cause). The agent file's `sonnet` is only the fallback. Give the worker a self-contained prompt (the goal, the files, the constraints, the check to run), since it does not see this conversation.
