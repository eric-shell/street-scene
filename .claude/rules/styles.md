# Stylesheet and UI markup (SCSS compiled by Vite through sass-embedded; plain DOM built in TS)

- `src/ui/styles/main.scss` is the whole stylesheet: the design notes and the conventions (read its header), the base layer (`styles/base/`: reset, tokens, document, the UI layer's states, shared keyframes), then one `@use` per area in cascade order. Each area's `_index.scss` uses its partials in their cascade order (`ui/kit`, `ui/rail`, `ui/menu`, `ui/splash`, `ui/screens`, `ui/transitions`, `ui/hud`, `src/garage`, `ui/panels`, `ui/map`). Only partials reached from there emit CSS; later rules win ties of specificity, so a new partial goes where its rules should win.
- Co-location: a partial sits beside the TS that builds its DOM and is named after its block (`ui/hud/_hud-card.scss` styles `.hud-card`, built by `ui/hud/hudCard.ts`), opening with a `/* ... */` comment that says what it styles and which module builds it. Partial names are unique within their folder's index.
- BEM: `.block`, `.block__element` (flat: `__stat-label`, never `__stat__label`), `.block--modifier` (a variant fixed at build), `.is-*` (a state the code toggles; chained, never alone; `body.is-*` for document states). Theme classes `.mode-*`, `.hue-*`, `.ink-*` set `--mode` / `--hue` / `--ink`. Full words, no prefixes like `g-` or `mw-`. In TS use the `ui/kit/dom.ts` helpers: `bem('chip', '--accent x')`, and `btn`, `iconBtn`, `chip`, `segmented`, `navRow`, `railScreen` take `--modifier` words in their `cls`. A class the code queries is the same BEM class the CSS uses; no separate hook classes.
- Nesting: one rule per block with `&__element`, `&--modifier`, `&.is-state`, pseudo-classes and the block's own media queries (`@include media.narrow { ... }` inside the rule it changes). At most three levels; the compiled selectors stay flat. A block restyled by its context is written in the context's partial.
- `abstracts/` emits no CSS: `_palette.scss` (the Monokai Pro colors, same names and values as `ui/kit/palette.ts`; keep both in step; `palette.alpha(orange, 0.35)`, `palette.rgb(cyan)`, `@include palette.tint(hue, red)`, `palette.$modes`), `_media.scss` (`@include media.narrow / phone / wide / short / very-short / compact-hud / touch / motion / reduced-motion`) and `_mixins.scss` (`chamfer($cut)` for every chamfered box, first in its rule; `rule-line($color, $lead)`; `plate`; `gradient-text`; `ellipsis`; `scroll-y`; `stagger($from, $to)`; `safe($side, $min)`; `sheen-on-hover`). Use them, and the tokens (`--ring`, `--plate-drop`, `--halo`, `--hud-halo`, `--well`, `--title-ink`, `--logo-ink`), instead of copying values; a one-off threshold one layout needs may stay literal.
- Runtime values stay custom properties (`--accent`, `--mode`, `--hue`, `--ink`, `--cut`, `--rail-*`): JS and the cascade change them. Sass variables, maps and loops are for compile-time tables only (race type, tab and nitrous stage hues). Inside a custom property Sass only evaluates `#{...}`, and it interpolates `#{...}` inside `/* */` comments too. Inside a mixin use `//` comments: a `/* */` one is emitted into every rule that includes it.
- Modern Sass only: `@use`/`@forward` (never `@import`), `sass:` modules (`color.change`, `list.append`, `map.get`), `@if` blocks (the `if()` function is deprecated). Quote palette names in maps and lists: `orange`, `red`, `green` are colors to Sass. The PostToolUse hook compiles the tree after every `.scss` edit and fails on any warning.
- No `!important`, ever (there are none). Win with specificity and order instead, and for reduced motion declare animations only inside `@include media.motion { ... }` (`prefers-reduced-motion: no-preference`); `media.reduced-motion` is for what else changes. HUD animations fade with `filter: opacity()` so the cinematic shots own `opacity`. An inline style set from TS is the one thing CSS cannot beat without `!important`: toggle a class instead.
- Specificity: a BEM modifier (`.btn--primary`, 0,1,0) is weaker than the compound it replaces (`.btn.primary`, 0,2,0), so a base state rule (`.btn:hover`) can start to win over it. Give modifiers their own state rules (`&--primary:hover`) after the base states.
- A refactor that should not change the look must not change the cascade (the `/refactor` skill has the tools): compile before and after and compare the rules canonically (each selector, property and value, and which rule wins where two can meet), not just the bytes. Check a visual change with `/dev` only when it cannot be judged from the code, and run the e2e spec for a screen only when a change could hide or block a control (`splash` for menu and splash); a styling tweak needs neither (CLAUDE.md, Checks).
